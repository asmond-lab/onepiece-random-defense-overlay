# ORDR 2.320 원본 분석 결과

## 결론

**원본 읽기 차단을 해결했고, 2.320의 실제 한국어 JASS와 7개 추가 멤버를 확보·검증했다.** 이전의 ‘새 맵 원본을 읽지 못함’ 결론은 더 이상 현재 상태가 아니다.

이번 결과는 파일명이나 패치노트만 보고 만든 추정이 아니다. 동일한 2.314 대조군, 원본/추출물 SHA-256, 전체 구문 검사, 오브젝트 전수 파싱, 실제 호출·조건·수치 대조를 사용했다. 다만 **오프라인 원본 분석과 실전 동작 검증은 구분**한다. 실행 중인 Warcraft 3.0 지원 승인, 랜디픽 운영 데이터 전환 또는 새 배포를 수행한 것은 아니다.

## 1. 분석 대상과 검증

- 대상: `ORDR_S2_2.320[R].w3x`, 119,129,261 bytes
- 맵 SHA-256: `68445631FDACA12A343E9465E5BC5DC9B4C8C6CC927D701F52E2CB822821E15F`
- 한국어 `war3map.j`: 3,014,709 bytes
- JASS SHA-256: `6FDFC64BF8AD9463F5B5C8A351FFA7E1875D6CF9B51210129539375FA77A6C7C`
- 대조군: 2.314, 맵 SHA `F9DDD3AF7C0FBFD39B7A6DF2CA0F5F295675BBA5E8B91A5322DCEC93D7CA8A83`
- 대조군 JASS SHA: `0BCCC47907A9505F38EFAF6BBF20228A728EABDFAEC3209CCA7DF2269BFC2028`
- 읽은 멤버: JASS, W3U(유닛), W3A(능력), WTS(문자열), Misc, W3T(아이템), W3Q(업그레이드), W3I(정보). 두 버전 각각 8개.
- 두 원본 맵은 읽기 전후 해시가 동일하다. 게임 입력·메모리 쓰기·인젝션·맵 실행·원본/헤더 수정은 없었다.

### 왜 기존 읽기가 실패했나

2.320의 해시 테이블에는 같은 이름의 범위 밖 블록 참조가 정상 참조보다 앞에 있다. `war3map.j`의 첫 참조는 3,183,628,222인데 실제 블록 개수는 64,749다. War3Net 6.0.3의 `FileExists`는 이를 범위 검사 없이 역참조했다. 구 SFmpq도 첫 조회에서 종료됐다. 이는 당시 **스크립트 복호화·압축 해제조차 도달하지 못한 조회 실패**였다.

정상적인 현행 StormLib API는 유효한 멤버를 읽는다. JASS는 언어도 중요했다. 중립 언어의 88-byte 항목과 한국어(1042)의 실제 3MB 항목이 별개다. `SFileSetLocale(1042)`와 일반 읽기 API로 실제 스크립트를 읽었다. 헤더 복구나 대체 키 사용은 없었다. 자세한 라이브러리 출처·정확한 DLL 해시·버전 표기 차이는 `modern-reader/confirmed-source-manifest.json`에 기록했다.

### 전체 파싱 결과

| 항목 | 2.314 | 2.320 | 확인 |
|---|---:|---:|---|
| JASS 함수 | 2,694 | 2,650 | 전체 파일 구문 오류 0 |
| 전역 변수 | 3,823 | 3,936 | 배열 629→685 |
| 유닛 오브젝트 | 1,411 | 1,518 | 추가107, 제거0, 기존 유효값 변경107 |
| 능력 오브젝트 | 1,644 | 1,672 | 추가28, 제거0, 기존 유효값 변경143 |
| 문자열 | 10,646 | 10,990 | 추가356, 제거12, 본문 변경175 |
| 아이템 | 14 | 15 | 환전소 `I009` 추가, 기존2개 이름/문장 변경 |
| 업그레이드 | 110 | 110 | 수치 변경0, 12개 참조 표현만 변경 |

‘유효값 변경’에는 툴팁·외형도 포함하므로 전부 밸런스 변경이라는 뜻은 아니다. 단순 바이너리 변경은 유닛799/능력308개지만, 동일한 문자열의 참조 표현 변경을 분리했다. W3I와 Misc는 두 버전이 동일하다.

WTS는 두 버전 모두 같은 5개 주석에만 잘린 UTF-8이 있다. **실제 문자열 본문은 모두 엄격 UTF-8 검증을 통과**했다. 주석 바이트를 보존하고 본문을 손실 치환하지 않았다.

JASS는 공식 War3Net.CodeAnalysis.Jass 6.0.2로 두 파일 전체를 파싱했고, AST로 복원한 텍스트가 원문과 일치했다. 뒤에 쓰레기 문자를 추가한 음성 대조는 실패했다. 구문 검사는 타입/이름 해석이나 실전 효과 검사가 아니다. 함수 난독화 이름이 거의 전부 바뀌었으므로 이름 기준 추가/삭제를 곧바로 기능 변화로 해석하지 않았다.

## 2. 반드시 구분해야 할 설명과 원본의 불일치

| 항목 | 표시/설명 | 확인된 원본 |
|---|---|---|
| 불릿 특강 | 48% / 방깎48 | 선택되는 능력4레벨 데이터는 **50% / 방깎50** |
| 불릿 연타 피해 설명 | 공격 강화에 연동하는 문구 | 실제 연타식은 **공속 능력 레벨** 사용 |
| 환전소 일반 탐색 | 2포인트 | 실행 핸들러는 **3 차감** |
| 환전소 특별 탐색 | 6포인트 | 실행 핸들러는 **10 차감** |
| 기본 레오 이감 | 패치노트10%, 보드7 | 오브젝트는 **10%**, 보드 등록은 구값7 |
| 계엄령 레오 | 강화 효과 | 능력2레벨은 **20%**, 보드는 해당 레벨 등록이 없어 **이 기여분0** |
| 강화 불릿 방깎 보드 | 방깎 총합처럼 보임 | A0WN은 **1레벨5만 등록**, 2/3/4레벨 기여분 누락 |
| 악몽 새턴 안내 | 기존30만 문구 | 데이터의 새턴 추가분은 **35만** |

위 능력 값은 **설정된 오브젝트 값과 실제 선택 코드**의 대조이지, 대상별 최종 이동속도·HP 감소·힐량을 실측했다는 주장이 아니다. 보드의 ‘0’도 그 능력의 보드 기여분이며 전체 캐릭터 수치가 0이라는 뜻이 아니다.

## 3. 불릿: 대깨 운영에 직접 영향을 주는 변경

정확한 ID는 native `h081`, 앱 `rawcode:180h`다. `h018`은 징베이며 혼동하면 안 된다. 불릿 유닛 오브젝트 자체는 같지만 관련 능력·스크립트가 바뀌었다.

### 단순 아이템 개수 비례가 아니다

연계 피해식은 `GetUnitAbilityLevel`을 읽는다. 새 `NfT`(24023–24029)는 3보다 높은 값을 3으로 제한한다. 공격은 A0WQ, 공속은 A0WO다. 아이템 충전량15~29는 같은2레벨이고 최대 충전 후 아이템이 바뀌어도 연계 계수가0이 되는 모델이 아니다.

다음은 **능력3레벨일 때 피해 래퍼 적용 전 표현식 값**이다. 최종 피해 보장은 아니다.

| 효과 | 이전 | 신규 |
|---|---:|---:|
| 공속 전설 범위 타격 | 63,500 | 185,000 |
| 공속 추가 단일 타격 | 30,000 | 300,000 |
| 스트라이크 첫 타격 | 1,725,000 | 3,750,000 |
| 스트라이크 반복 1회 | 103,000 | 130,000, 12회 |

7개 연결 피해식의 정확한 신구 수식과 호출·대상 조건은 `bullet-nika-analysis.md`에 있다. 모두 일괄10배가 아니다. 레벨0~4 경계 **35사례**를 이상 소수값, float64, 명시적 binary32 모델로 검사했다. 신규 레벨4의 연계식 결과는3과 같다. 레벨0/구 레벨4 계산은 수식 경계 검사이지 그 상태에서 스킬이 발동한다는 뜻이 아니다.

### 강화·특강

- 충전15/30의 기본 단계 구조는 유지된다. 새 내부 배열은 공격Zn/공속fn/방깎Bn이다.
- 신규 선택 경로 A203→A207, 선택 A204/A205/A206은 특성 포인트4를 사용하고, 선택 능력이3레벨일 때4로 만든다.
- 실제 선택되는4레벨은 공격50%·공속50%·방깎50이다. 연계 피해는 위3레벨 제한을 받는다.
- 충전 핸들러의 내부 +1과 무작위 증가는 아이템 사용 시 엔진의 차감과 구분해야 한다. 최종 획득량을 코드 한 줄만 보고 +2/+3으로 바꾸지 않는다.
- 기존 방깎→공속 우선 정책이 여전히 최적인지는 이 패치만으로 증명되지 않는다. 공격 관련 변화가 커서 정책 재평가 대상이지 임의 우선순위 반전의 근거는 아니다.

## 4. 니카: 조합 조건과 오로성 상호작용

### 조합

신규 `MHy`(22944–23071)는 플레이어 강화 플래그 `sg!=0`을 **재료 소모 전에** 요구한다. 플래그는 루피/스네이크맨 강화 경로에서1, 니카 제작 성공 시2가 된다. 이것은 정확히 소모되는 유닛 핸들의 강화 여부를 다시 검사하는 것과 다르다.

이전 ET02/ET03 두 조합은 새 ET02와 H08T 별칭으로 정리됐다. H08T는 실제 루피 H099 또는 스네이크맨 H0B2를 인덱싱하는 ‘루피 or 스네이크맨’ 선택지다. 보드에 별도 H08T 유닛이 필요하다고 추천하면 안 된다. ITEM 조건도 실제 가방 개수가 아니라 플레이어 보유 토큰의 boolean 0/1이다. 기존 TMO 아이템 ID와 JASS 토큰은 별도 매핑 검증 대상이다.

### 오로성 억제/해제

연결까지 추적했다. 등록된 오로성 핸들러 `vYb`(76072–76255)는 50라운드 전환 경로에서 플레이어0~3 중 **니카 제작 완료 플래그 sg==2가 있는지** 검사한다. 있으면 오로성 효과 적용을 건너뛰고 에메트 연출 및 표시 오로성 제거 경로로 간다. 본인의 생존 니카를 매번 검색하는 조건은 아니다.

오로성 효과가 이미 적용된 후 니카 제작이 성공하면 관련 전역값·오라·연구 상태를 즉시 복원하고, 에메트 연출은15초 뒤로 예약한다. **15초 뒤에야 전역 효과를 해제하는 것은 아니다.** 다만 기존 적에게 이미 복사된 A04Q/A11S 레벨을 일괄 재작성하지 않는다. 기존 적의 모든 효과·HP가 즉시 완전히 원상복구된다고 보장하지 않는다. 상세 적용 대상·상태 전이와 구버전 부재 대조는 `nika-interaction-evidence.json` 및 상세 보고서에 있다.

## 5. 항법·도박·스토리·미션

### 환전소

연속배팅의 이름만 바뀐 것이 아니다. 중급도박 시도마다 성공/실패와 관계없이1포인트를 먼저 얻는다. 아래는 **실행 코드의 차감/보상**이다.

| 메뉴 능력 | 포인트 | 보상 |
|---|---:|---|
| A0CI | 1 | 1~5 분기:4~5 골드5000,2~3 랜덤위습1,1 선택위습1 |
| A0EZ | 3 | 목재1~2 |
| A0DB | 3 | 선택위습1~2 |
| A0IY | 5 | 배1 |
| A0JR | 3 | 일반 탐색1, 이후 버튼 비활성화 |
| A0BV | 10 | 특별 탐색1, 이후 버튼 비활성화 |
| A0MA | 20 | 이세계 풀 유닛1과 토큰1 |

일반/특별 탐색은 툴팁2/6과 실행 차감3/10이 다르다. 스택 한도 검사보다 포인트 차감이 앞서고 해당 핸들러에 환불은 없다. 이는 코드 순서 확인이며 모든 만스택 UI 상황을 재현한 것은 아니다. ‘한 판1회’는 재활성화 경로를 전수 추적하지 않아 확정하지 않았다. 7개 메뉴 쿨다운은 약0.2초이고 마나는 기반 ANcl 상속값이 미확인이라0으로 채우지 않았다. 무작위 분기 범위는 확인했지만 완전 균등 분포를 증명한 것은 아니다.

### 나머지 핵심

- 이세계 기본 성공 기준 **22→15**, 리스크헷지 실패 보정 **11→15**. 성공하면 보정 초기화.
- 카지노 선택 시 잔여 횟수는 단순2배가 아니라 **2×잔여+이미 소비한 횟수**. 이후 해당 횟수 지급은 기존1 대신2.
- 정의의문3단계 크립 미션은 귀속 플레이어에게1회 충전을 준다. 모든 처치가 무조건 충전이라는 뜻은 아니다.
- 패왕의길은 레오 `h0C8` 소환으로 바뀌고, 기존 보스 추가목재2는 짝지은 보스 핸들러에서 제거됐다. 계엄령은 레오 A0II를2레벨로 만든다. 기존 상위 제작 제한은 유지된다.
- 일석이조 소급 보상은 현재 생존 패 수가 아니라 **해당 누적 제작 카운터 합계당 추가 랜덤위습1**이다. 미래 제작의 기본+추가 지급과 구분해야 한다.
- 첫3개 스토리의 기여도 보너스 위습은 활성 플레이어 모두에게 지급. 이후 기준은 완료 시 사람 플레이어 수에 따라2인30%,3인25%, 그 외20%. MVP 보상까지 전원 지급으로 바뀐 것은 아니다.
- 개인미션 리롤은 **라운드<10, 플레이어당1회, 미완료·비어 있지 않은 슬롯**. Q017 신비 조합 미션의 이세계 모드 포함 조건도 확인했다.
- 신속한철거는 알라바스타 n002, **마지막 유효 라운드8**, 9라운드부터 거부한다.

## 6. 신규 패 수치 보드는 실제 전투 합계와 다르다

공식 보드 알고리즘용 데이터 **221행·199능력·156개 정적 유닛 연결**을 추출했다. 모든 등록 능력 오브젝트가 존재한다. 부모 검증에서221행 전부를 JASS로부터 독립 재파싱해 일치 확인했다.

- 소유자·생존·유닛 분류·실제 능력/레벨이 자격 조건이다. 인벤토리 rawcode와 수량만으로 항상 재현할 수 없다.
- 능력 레벨은 **정확히 같은 행**만 인정한다.
- 같은 능력의 여러 레벨이 있으면 **낮은 등록 레벨**, 같은 효과 가족은 **절댓값이 작은 값**을 선택한다. 의도인지 버그인지 단정하지 않고 원문대로 기록했다.
- 개수만큼 곱하지 않는다. 발동 중인지, 실제 대상/범위, 유지시간, 확률, 상한을 검사하지 않는다.
- 방깎 오라 / 발동 방깎 / 이감 오라 / 발동 이감을 분리한다. 첫 ‘방어력 감소 합계’에는 발동 방깎이 더해지지 않는다.
- 스펙은 수동 갱신이며5초 재사용 제한. 스토리 기여도는 별도0.25초 갱신이므로 **기여도는 최신인데 스펙은 오래된 상태**가 가능하다.
- 레오/강화 불릿 누락과 더 약한 효과 선택이 확인돼, 보드 수치를 전투의 절대 정답으로 삼으면 안 된다.

기존 랜디픽 TMO48784 프로필은 일부 비중첩 가족의 최댓값을 사용한다. 이 보드는 최솟값 선택, 능력 존재/레벨 기반이므로 서로 다른 모델이다. 기존 수치를 덮어쓰지 말고 ‘2.320 인게임 보드 재현’과 ‘출처별 패 수치’를 구분해야 한다.
